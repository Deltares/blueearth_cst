# Test-suite bloat and coverage assessment — 2026-08-11

Scope: `tests/`, plus the source it covers. Questions asked: *assess the
coverage; identify redundancies and tests that are no longer needed (written for
a one-time migration or a specific refactoring job).*

Read §1 and §2 before the tiers — the answer is not the one the raw count
suggests, and the tightest lever is not the one the question implies.

Evidence base: full suite run on this worktree (fixtures present — `test_local`
and `basin_map_fixture` seeded), `pytest tests/ -q --durations=60`:
**2,030 passed, 6 skipped, 1 xfailed in 435.75 s (7 min 15 s).** Only 6 skips, so
this is a *full-strength* gate, not the degraded worktree run AGENTS.md warns of.

## 1. What "2,000 tests" actually is

| Measure | Value |
|---|---|
| Collected items | **2,037** |
| `def test_` functions | **1,428** |
| Items generated by `parametrize` expansion | ~609 (30%) |
| Test files | **114** |
| Test lines | **27,257** |
| Source modules under test | 102 |
| Wall-clock | **435.75 s** |

**~30% of the count is parametrize expansion, not authored tests.** Five files
generate more than twice their function count: `test_script_module_importability.py`
(3 functions → 71 items, one per shipped module), `test_project_tree_inventory.py`
(8 → 102), `test_r09_path_map.py` (25 → 97), `test_plot_map.py` (121 → 163),
`test_indicator_tables.py` (21 → 39). An expansion is a row in a table, not a
function to keep true. Counting them as "tests to prune" overstates the
maintenance surface by about a third.

The honest denominator is **1,428 functions across 27k lines**, not 2,037.

## 2. Redundancy: effectively zero

An AST scan hashed every test function body (docstring stripped) across all 114
files, looking for identical bodies in different files. **Three groups matched;
all three are false positives:**

| Pair | Verdict |
|---|---|
| `test_region_rule::test_defaults_match_the_spatial_contract` ↔ `test_snake_utils::test_climate_store_rule_hydrography_defaults_match_the_spatial_contract` | Identical body, different `_spec()` helper — one builds `region_rule`, the other `climate_store_rule`. Two rules, one shared contract. **Not redundant.** |
| the `_overrides_are_carried_through` twin of the above | Same. **Not redundant.** |
| `test_every_workflow_declares_the_rule` in `test_region_rule` ↔ `test_spatial_units_rule` | Same instrument, different `RULE_NAME` module constant. **Not redundant.** |

Eleven test *names* repeat across files (`test_declarations_are_identical`,
`test_within_absolute_tolerance_passes`, …); each is the same instrument applied
to a different subject — a deliberately templated contract-test pattern.

**There is no meaningful redundancy to cut.** Any reduction must come from
retiring subjects, not from deduplicating assertions.

## 3. The real cost is concentrated in four tests, not spread over 2,000

The durations profile is extremely top-heavy:

| Test | s | % of run |
|---|---:|---:|
| `test_climate_store_freshness::test_catalog_edit_schedules_extraction_exactly_once` | 53.6 | 12.3% |
| `test_guard_invalidation::test_guard_invalidation_i_to_l` | 44.6 | 10.2% |
| `test_guard_invalidation::test_2c_fresh_project_missing_wf1_snapshot` | 32.5 | 7.5% |
| `test_climate_store_freshness::test_alternating_workflows_never_reextract` | 28.2 | 6.5% |
| **subtotal (4 tests)** | **158.9** | **36.5%** |
| next 6 (`test_cross_workflow_inputs` ×3, `test_cli` ×3) | ~70 | 16% |
| **top 10** | **~229** | **53%** |

All ten drive **repeated Snakemake dry-run subprocesses**. The remaining ~2,020
items together cost under half the run. Every `test_plot_map` item is ≤ 1.1 s;
most are milliseconds.

**Implication for the question as asked:** deleting tests will not make the
suite noticeably faster. Deleting Tier 1 below (~106 items) removes well under
1 s of wall-clock. If *runtime* is the goal, the lever is amortising the
Snakemake subprocess in those four tests (a session-scoped dry-run fixture), not
pruning count. That is a separate piece of work and is **not** proposed here.

## 5. Milestone tags are provenance, not staleness

Sixty of the 114 files carry a milestone ID in their docstring (`R3 §8`,
`R07 B1`, `p32b §5.5`, `[R7-22]`, "Falsifiers M1–M4"). That is why the suite
*reads* legacy-heavy. Mostly it is not: those docstrings record **why a test was
written**, while the property under test is live. `test_snake_utils.py` opens
"pins the semantics the four inline `get_config` copies had before they were
collapsed" — an R3 refactor framing on 80 tests of a helper that 17 test files
and all three Snakefiles still route through.

The R8 falsifier files are the clearest case and must **not** be cut:
`test_a1_acceptance`, `test_hydrological_year_bounds`, `test_statistic_set`,
`test_monthly_change`, `test_grid_weights`, `test_calendar_weights`,
`test_reference_window`, `test_store_calendar`, `test_dry_month`,
`test_variable_spec` (99 items). Each pins WF2 arithmetic that was *measurably
wrong at least once* — the January hydrological-year case returned 29 where the
design says 30, until 2026-07-30.

**The discriminator between a retirable migration test and a live one is not the
milestone tag. It is whether the test can only be exercised against a state of
the world that no longer exists.** One cluster meets that test.

114 files for 102 source modules, and the split does not follow the modules:

The pattern is one file per *milestone step*, not per subject. Merging would take

and destroys the `git log --follow` provenance the milestone docstrings depend

Recommendation: **do not consolidate as a project.** Merge opportunistically —
when a task already edits one of a pair, fold the 60-line sibling in then. The
`check_baseline` four-way split is coherent as-is and should stay.
