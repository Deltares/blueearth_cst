> **What** — TWO defects under one title, separated 2026-08-18 by capturing
> both. The FAILURE is a Windows rename race in zarr's metadata write
> (`provenance:zarr`), diagnosed and fixed the same day. The STALL is a hang in
> the netCDF glob scenario, and it is now DIAGNOSED: `_run_glob` writes netCDF

**Why that line and not another.** `_write_source` does `shutil.rmtree(path)`
and then recreates the SAME store path, and `_rebuild_provenance` is the one
scenario that calls it twice on one path — write the source, stage it, then
mutate the 2001 overlap and re-stage to prove 2001 is not re-read. Delete-then-
recreate-the-same-path is where Windows delete-pending handles and AV/indexer
scans bite: the fresh `zarr.json` is renamed over a path the OS may still hold.

**The finding that changes what the fix is: the retry is in the wrong place.**

failure is not in the product at all — it is in the harness's own fixture
writer, which has no retry, and it is not a dask write path but zarr's own
asyncio metadata write. The product's retry is, as a consequence, NOT exercised
by this test.

## The stall, diagnosed (2026-08-18)

`faulthandler` did in one occurrence what six weeks of waiting could not. Two
stacks, both from the stalled child:

**The main thread — waiting on its own workers:**

```
_stage_equiv_harness.py:432  <module>
_stage_equiv_harness.py:415  main
_stage_equiv_harness.py:189  scenario_glob
_stage_equiv_harness.py:70   _stage
stage_data.py:1688  stage
stage_data.py:1638  _stage_dataset
stage_data.py:1601  _stage_netcdf_glob
stage_data.py:1495  _run_glob
concurrent/futures/_base.py:243  as_completed   <- blocked here
```

**A worker thread — blocked opening a netCDF file for writing:**

```
concurrent/futures/thread.py:93  _worker
stage_data.py:1180  _worker_result
stage_data.py:500   wrapper
stage_data.py:1142  subset_netcdf_file
stage_data.py:1083  _clip_netcdf_to_file      <- sub.to_netcdf(dst)
xarray/core/dataset.py:2134   to_netcdf
xarray/backends/writers.py:422  to_netcdf
xarray/backends/writers.py:78   get_writable_netcdf_store
xarray/backends/netCDF4_.py:529 open
xarray/backends/netCDF4_.py:429 __init__       <- blocked here
```

**So: `_run_glob` writes netCDF from SEVERAL THREADS AT ONCE.** It runs
`subset_netcdf_file` across a `ThreadPoolExecutor` (`workers`), and each worker
ends in `sub.to_netcdf(dst)`. HDF5 is not thread-safe, and netCDF4-python
serialises through a global lock — so concurrent opens contend, and on Windows
one of them stops coming back. The main thread then waits in `as_completed`
forever, which is why the process is silent rather than busy.

**This is the same family as the CHIRPS deadlock** fixed in `b03d965` ("write
the climate store synchronously to break a netCDF deadlock"). Same engine, same
remedy shape: take the concurrency out of the write.

**Why the harness's existing dodge could never have helped.** `_stage` pins
`dask.config.set(scheduler="synchronous")`, and that governs DASK's threads.
The pool that deadlocks here is `stage_data`'s OWN `ThreadPoolExecutor`, which
dask config does not touch. The comment in `_stage` claiming the synchronous
scheduler "sidesteps" the flakiness is therefore true of the zarr rename and
false of this.

**Blast radius, and why the fix is not test-only.** `dev/scripts/stage_data.py`
is what stages CMIP6 slices for fixtures and for real. Anyone running a
multi-file `netcdf_glob` stage with `workers > 1` on Windows is exposed to the
same hang; the test is just the reproducer that happens to run often. Fix
candidates, cheapest first: one module-level `threading.Lock` held across
`to_netcdf` (keeps the parallel clip, serialises only the write); force
`workers=1` for `netcdf_glob`; or hand xarray an explicit per-file lock. The
first preserves most of the parallelism the pool was added for.
