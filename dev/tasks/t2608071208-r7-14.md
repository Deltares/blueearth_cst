> [!note] Overview
> **What** — `tests/test_stage_data_incremental.py` failed under some orderings
> through 2026-08-02. It did not reproduce once in a deliberate hunt on
> 2026-08-09, so it is demoted from work to watch rather than fixed blind.
> **Why** — A speculative fix for an unreproduced flake is worse than none: it
> lands a retry or a sleep that nobody can ever remove, and that hides the next
> real defect in the same code path.
> **Trigger** — It actually fails again. **Capture the full pytest output AND
> the ordering that produced it** before re-running — that is precisely the
> evidence this hunt lacked, and a re-run destroys it.

## What was tried, 2026-08-09

Load varied widely during those runs — a concurrent session in another worktree

chance to show and did not.

## Where to look first if it returns

1. **A race, not a stub.** The obvious `sys.modules` explanation is already
   handled: this test shells out to `tests/_stage_equiv_harness.py` in a
   subprocess *specifically* so the real xarray is used rather than the
   lightweight mock `test_stage_data.py` installs at import. The harness also
   forces `dask.config.set(scheduler="synchronous")` to sidestep the concurrent
   zarr-v3 metadata renames that are flaky on Windows — see `94e63cd`,
   "stage_data: retry flaky zarr-v3 metadata rename on Windows". If it fails
   again, that retry path is the first suspect.
2. **The one order-dependence that is real.** Importing `stage_data` mutates the
   *parent's* `os.environ` — `GDAL_CACHEMAX`, `VSI_CACHE`, `VSI_CACHE_SIZE`,
   `GDAL_DISABLE_READDIR_ON_OPEN`, all via `setdefault` — and this test passes
   `{**os.environ, ...}` straight to the child. So the child's GDAL config
   genuinely differs depending on whether an earlier test imported `stage_data`
   in-process. Deliberately NOT "fixed" in 2026-08-09: those are raster-path
   variables and the harness is xarray/zarr/netCDF, so the channel is real but
   the mechanism is not plausible. It is written down here rather than patched
   so that a future failure can rule it in or out in one step.
3. **Not persisted state.** Everything the harness writes stays under the
   pytest `tmp_path` it is handed, so "passes on re-run" cannot be explained by
   leftover files.
