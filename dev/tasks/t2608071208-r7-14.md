> [!note] Overview
> **What** — The child process driven by `tests/_stage_equiv_harness.py` stalls
> indefinitely, sometimes. Contained on 2026-08-09 (`ea2e430`) but not fixed:
> the stall itself is undiagnosed.
> **Why** — It took the windows CI leg down for 30 minutes and turned `main`
> red on a README rename. Containment makes the next occurrence legible; it
> does not stop it happening.
> **Effort** — Small once it recurs with the new markers; the diagnosis is the
> work, not the fix.

## Progress

**RE-OPENED 2026-08-09, having been demoted to a watch-item earlier the same
day.** The demotion was wrong, and the way it was wrong is the useful part:

- The hunt that justified it ran this test **15 times across 5 orderings** and
  counted **failures**. Zero.
- The failure mode is an **unbounded wait**. A hang never produces a failure, so
  the hunt could not have found it however long it ran. Right method, wrong
  target.

**The occurrence, in full** (CI run `31330093862`, `32c3a42`, windows-latest):

| | |
|---|---|
| suite reached 89 % | 18:56:55Z |
| further output | none, for 24 minutes |
| job killed | 19:21:16Z, by `timeout-minutes: 30` |
| ubuntu leg | passed normally |
| same code, 2 h earlier | windows leg green in **6m37s** (`4a5e2cc`) |

`32c3a42` differs from `4a5e2cc` only by renaming `README.rst` to `README.md`
and two lines of AGENTS.md prose, so the hang is unrelated to what was pushed.
The 88–92 % band of the collection contains this test, and it is the only test
there that spawns a subprocess.

**Contained, not fixed** (`ea2e430`): the child now has `timeout=600`, and the
harness prints a flushed `STEP <name>` per scenario. Verified: a deliberate 20 s
kill now captures 1193 chars including `STEP glob`, where the same probe
returned an empty string before — `capture_output=True` is a pipe, so unflushed
lines died with the killed child.

**A bounded failure finally happened — 2026-08-12, and the marker was thrown
away.** The containment worked exactly as designed: the harness **failed**
(`AssertionError: equivalence harness failed`) instead of hanging, in a local
`pixi run test-full` in `lane/pipeline`, at 91 % of collection — inside the
88–92 % band this note already names. It then passed standalone in 20 s and
passed in an immediate full re-run (2044 passed, 0 failed), so it remains
order-dependent and intermittent, and it is unrelated to that session's work
(a baseline re-record).

The `STEP` marker was **not** captured, because the suite had been run through
`... | tail -8` and pytest's failure detail scrolled past the retained lines.
For whoever catches the next one: **run the suite redirected to a file, never
piped through `tail`** — a bounded failure is rare enough that losing its output
costs another wait, and the marker is the whole point of `ea2e430`.

- [ ] **Wait for one bounded failure and read its `STEP` marker.** That names
      the scenario, which is the single fact every previous attempt lacked.
      Still open: the 2026-08-12 occurrence produced one and it was lost to a
      `tail` pipe.
- [ ] Prime suspect once localized: the zarr-v3 metadata rename race on Windows
      that `94e63cd` added a retry for, and that `_stage()` already tries to
      dodge via `dask.config.set(scheduler="synchronous")`
- [ ] Decide whether the retry in `stage_data` needs to cover the path the
      harness exercises, or whether the harness's synchronous-scheduler
      workaround is incomplete
