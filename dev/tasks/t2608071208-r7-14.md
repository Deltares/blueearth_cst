> **What** — TWO defects under one title, separated 2026-08-18 by capturing

**The scenario, named at last:** `_rebuild_provenance(work / "pv_zarr", "zarr",
as_zarr=True)` — the **zarr** leg. Not the glob scenario, and not netcdf.

**The call site, verbatim:**

```
_stage_equiv_harness.py:368  main
_stage_equiv_harness.py:210  _rebuild_provenance   <- the SECOND _write_source
_stage_equiv_harness.py:81   _write_source         <- ds.to_zarr(path, consolidated=True, mode="w")
  xarray -> zarr.consolidate_metadata -> group._save_metadata
  -> asyncio.gather(*set_awaitables) -> asyncio.to_thread(_put)
  zarr/storage/_local.py:74  _atomic_write -> tmp_path.replace(path)
PermissionError: [WinError 5] Access is denied:
  ...\pv_zarr\src\meteo\prov_zarr.zarr\zarr.46ec38929b3344879779085c6ee13de2.partial
  -> ...\pv_zarr\src\meteo\prov_zarr.zarr\zarr.json
```

**Why that line and not another.** `_write_source` does `shutil.rmtree(path)`
and then recreates the SAME store path, and `_rebuild_provenance` is the one
scenario that calls it twice on one path — write the source, stage it, then
mutate the 2001 overlap and re-stage to prove 2001 is not re-read. Delete-then-
recreate-the-same-path is where Windows delete-pending handles and AV/indexer
scans bite: the fresh `zarr.json` is renamed over a path the OS may still hold.

**The finding that changes what the fix is: the retry is in the wrong place.**
`94e63cd` added a retry inside `stage_data`, and `_stage()` dodges via
`dask.config.set(scheduler="synchronous")`. **Neither covers this**, because the
failure is not in the product at all — it is in the harness's own fixture
writer, which has no retry, and it is not a dask write path but zarr's own
asyncio metadata write. The product's retry is, as a consequence, NOT exercised
by this test.

**Still unproven:** whether the original 24-minute CI *hang* shares this root
cause. This occurrence and the two before it are bounded FAILURES (nonzero rc
with a traceback), which the harness reports differently from a stall
(`TimeoutExpired`). A retry loop around a denied rename is a plausible bridge
between the two, and that is all it is — a hypothesis.

**Not verified:** whether the other session slot was running its own suite
concurrently. Two suites would raise handle/AV pressure on `%TEMP%`, which would
fit an intermittent rename denial, but nothing was recorded either way.

**So the two failure modes are different defects.** The bounded FAILURE dies in
`provenance:zarr` on a zarr metadata rename; the STALL hangs in `scenario_glob`,
in the **netCDF** path, with no zarr write anywhere near it. The caveat this
note recorded above — "a retry loop around a denied rename is a plausible
bridge, and that is all it is" — is now answered: it is not the bridge. The zarr
retry cannot fix the hang, and the hang was never zarr's.

**Where it hangs, precisely:** the start of the WIDEN stage, before a single one
of the 6 files is processed. Everything the widen stage needs to inspect at that
point was written seconds earlier by the narrow stage in the same run, which
points at a handle on a just-closed netCDF file rather than at anything the
staging logic decides. HDF5/netCDF file locking on Windows and an antivirus
holding a newly-created file are both consistent with the evidence; neither is
proven.

**A REPRODUCTION RECIPE, which is the thing this note has never had:** run
`pytest tests/test_stage_data_incremental.py` three times in a row. It stalled
on the **third** run in 2 of 3 attempted sequences today (one with an unrelated
harness change applied, one without; a third sequence ran 5/5 clean). Two
occurrences in six weeks became two in one hour. Worth suspecting pytest's own
tmpdir garbage collection, which keeps the three most recent `pytest-of-<user>/
pytest-NNNN` trees and starts deleting older ones exactly when a third run
begins — deleting a tree full of netCDF and zarr stores while a new run creates
more, under the same antivirus.
