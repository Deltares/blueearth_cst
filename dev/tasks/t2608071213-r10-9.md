> [!note] Overview
> **What** — Define one label constant per rule, so a rename is a one-line edit.
> **Why** — FOUR call sites per rule repeat the same label today — `rule_banner`, `log:`, `benchmark:` and the `LOG_RULES` entry — which is how stale and unlisted labels kept appearing.
> **Effort** — Medium. ~55 rules across all four `*.smk`, so it is a sweep touching every workflow entry point and takes `test-full` at the merge. **No longer blocked** — see the 2026-08-20 correction below.

## The blocker is gone — measured 2026-08-20

**The Detail section below is the verbatim R10-9 entry and is left unedited.
Three of its claims are now known to be wrong, and this section is the
correction.**

- **"Six call sites per rule" is four**: `message: rule_banner("0.02",
  "delineate_region")`, the `log:` path, the `benchmark:` path, and the
  `LOG_RULES` entry.
- **"Three consumers read it out of source text" is two.** The third,
  `tests/test_experiment_config.py`, had its `LOG_RULES` half REMOVED at the
  `[R10-5]` renumber and says so in its own docstring. It still slices Snakefile
  source, but for an `output:` declaration, not the label list.
- **"`LOG_RULES` must stay a list literal" is false, and backwards.**
  `workflow.globals["LOG_RULES"]` is reachable after
  `workflow.include(...)`, verified on all four Snakefiles. Reading the
  literal was not a constraint to preserve but a DEFECT: `analyze_climate.smk`
  appends `0.06_compare_climate_sources` at parse time, so the literal is five
  entries while a multi-source run merges six, and a literal parser cannot see a
  statement. That blindness is exactly why a second parser had grown in
  `tests/test_compare_climate_sources.py` — the duplication `[R10-10]` warns
  about, caused by the very rule this note treated as sacred.

`tests/test_log_rules_contract.py` now reads the parsed workflow, is
parametrized over `(snakefile, config variant)` so WF0 is checked under both a
single- and a two-source config, and derives both sides of every comparison
from one cached parse. The duplicate regex is retired. Cases went 16 -> 20.

**What remains is only the sweep**, and one constraint it must respect: the
contract asserts `LOG_RULES` reads in rule-number order. A registry that
accumulates in call order couples that to SOURCE order invisibly — reordering
two rules would silently change the merge order rather than failing the check.
Either sort in the registry and assert it matches call order, or build only
`rule_banner`/`log:`/`benchmark:` from constants and leave the list explicit,
which is three sites rather than four and makes a rename a two-line edit.

## Detail

**[R10-9] Make the `LOG_RULES` contract a test.** **The test is DONE
2026-08-06** — `tests/test_log_rules_contract.py` asserts set-equality between
each Snakefile's `LOG_RULES` and the labels derived from every rule's `log:`
path, plus, since the `[R10-5]` renumber, that the list reads in rule-number
order. It confirmed `[R10-8]`'s deletion left no orphan. The
unlisted-or-stale-label defect had occurred four times before it existed.

**Still open: one label constant per rule.** Defining
`_L = "1.10_add_climate_forcing"` and building `LOG_RULES`, `rule_banner`,
`log:` and `benchmark:` from it would collapse four of the six call sites per
rule and make the next rename a one-line edit. The R10 sweep was the moment
this was free and dropped it anyway, so the reason matters: **`LOG_RULES` must
stay a module-level list literal.** Three consumers read it out of the source
text without executing the Snakefile — a Snakefile is not valid Python, so
`ast.literal_eval` on the lifted block is the only way to read it. Building the
list from per-rule constants makes it a list of *names* and `literal_eval`
raises. Closing this needs the checker to parse the executed workflow's globals
instead — a change to the instrument, so do it as its own task, instrument
first.
